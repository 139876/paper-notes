## 0. 一句话结论

> [!tip] 记住这一句就够了
> **DeCoDet 真实域的 +12.4 mAP 里，+10.0 来自 PDFT（训练策略，零参数零算力），只有 +2.4 来自模型模块（MSDP / DCK / SIRLoss）。**
>
> 论文把这两件事放进**同一张消融表**，看起来像"我的方法涨了 12.4 点"；
> 但**它们的成本差了一个量级**：PDFT 是免费的，模块是 +1.9M 参数 / +46 GFLOPs。
> 👉 **复现和选题时，第一件事就是把这两类贡献拆开算账。**

第二个结论（对你更重要）：

> [!important] 🔥 DeCoDet 的优势**几乎全部在真实域**
> 合成域它只领先第二名 **+0.4 mAP**（52.0 vs Cascade R-CNN 51.6）；
> 真实域领先 **+1.5 mAP**（38.7 vs 37.2）。
> 👉 所以这篇论文真正证明的是「**域适应**」，不是「检测精度」。
> 它没有让检测器更会检测，它让检测器**更能跨过合成雾 → 真实雾那道坎**。

第三个结论（**最容易被表格骗到的**）：

> [!danger] 📌 Table 3 是「**统一协议 benchmark**」，不是「模型能力排名」
> 19 个模型里 **16 个都用了 PDFT** —— 也就是说 Table 3 里的差距，
> 有大半来自**同一个训练策略**，而不是各家的网络设计。
>
> 证据：Table 3 的 VFNet = **35.6**，Table 4 的 VFNet baseline = **25.6**，
> 同一个模型，**差 10.0 mAP** —— 这 10.0 就是 PDFT。
>
> 👉 **引用 Table 3 时必须说明"所有模型都在同一 PDFT 协议下训练"**，
> 否则读者会误以为 "DeCoDet 的网络本身比 VFNet 强 10 点"。

### 1.3 🔴 "constant warmup" 的真实语义（**最容易记反的一条**）

基座 `schedule_1x.py` 用的是**标准 LinearLR 升 warmup**：

```python
dict(type='LinearLR', start_factor=0.001, by_epoch=False, begin=0, end=500)
```

但 **DeCoDet 的 config 把整个 `param_scheduler` 列表覆盖掉了**，换成：

```python
dict(begin=0, by_epoch=False, end=1500, factor=0.3333333333333333, type='ConstantLR')
dict(type='MultiStepLR', begin=0, end=12, by_epoch=True, milestones=[8, 11], gamma=0.1)
```

#### ① 先说结论：**它不会和基类的 `LinearLR` 叠加**

MMEngine 的 config 合并规则（`Config._merge_a_into_b`）：

| 值的类型 | 合并方式 |
|---|---|
| `dict` | **递归合并**，子覆盖父 |
| **其它（含 `list`）** | **整体替换** `b[k] = v` |

`param_scheduler` 是 **list** → DeCoDet config 把基座的 `[LinearLR, MultiStepLR]`
**整个换成** `[ConstantLR, MultiStepLR]`。

> ✅ **基座那个 `LinearLR` warmup 在 DeCoDet 里根本不存在。**
> 👉 复现时以 config 为准，**别自己加 warmup**。

#### ② `ConstantLR` 到底怎么算（官方源码 `mmengine/core/optimizer/param_scheduler.py`）

```python
class ConstantParamScheduler:
    def __init__(self, factor=1./3, begin=0, end=INF, ...):
        self.total_iters = end - begin - 1
        self.factor = factor

    def _get_value(self):
        if self.last_step == 0:
            return group[self.param] * self.factor          # 第 0 步：乘 factor（÷3）
        if self.last_step > self.total_iters or self.last_step != self.total_iters:
            return group[self.param]                        # 窗口内：保持不变
        if self.last_step == self.total_iters:
            return group[self.param] * (1.0 / self.factor)  # 窗口末 iter：乘回（×3）
```

`step()` 里只有 `begin <= _global_step < end` 时才把值写回 lr。

#### ③ ⇒ 真实 lr 轨迹（VFNet 版，config lr = 0.02）

| iter | lr | 说明 |
|---|---|---|
| 0 | **0.006667** | 立刻 **÷3** |
| 1 – 1498 | **0.006667** | 保持不变（"constant" 指的就是这段） |
| **1499** | **0.02** | 窗口最后一 iter，**乘回满 lr（涨 3 倍）** |
| 1500 及以后 | 0.02 | 出窗口，调度器不再写回 |
| epoch 8 | 0.002 | MultiStepLR ×0.1 |
| epoch 11 | 0.0002 | MultiStepLR ×0.1 |

**换算成 epoch（8000 张训练图 ÷ 总 batch 16 = 500 iter/epoch）：**

```
epoch 1-3   iter    0..1499   lr = 0.006667   (1/3)  ← iter 1499 末跳回满 lr
epoch 4-7   iter 1500..3999   lr = 0.02      (满 lr)
epoch 8     iter 4000..4499   lr = 0.002     (×0.1)
epoch 9-10  iter 4500..5499   lr = 0.002
epoch 11    iter 5500..5999   lr = 0.0002    (×0.1)
epoch 12    iter 6000..6499   lr = 0.0002
```

#### ④ 🔴 论文措辞 vs 实现

| | 论文写的 | 实现真做的 |
|---|---|---|
| 措辞 | "a constant warmup" | **没有 warmup**：lr 在第 0 步就降到 1/3 |
| 窗口内 | — | lr = base ÷ 3，恒定不变 |
| 窗口结束后 | — | 跳回 base（**涨** 3 倍），不是继续衰减 |

> ⚠️ **MMEngine 自己的 docstring 也会骗人**：
> 官方写的是 "Decays the parameter value ... **by a small constant factor until** ... end"，
> 字面意思是"到 end 之前一直衰减" —— **和实现不符**（实现是"到 end 那一 iter 就还原"）。
> 👉 **别信 docstring，去读 `_get_value()`。**
>
> 📌 **一句话记忆**：`ConstantLR` = "**先 ÷factor 冻住，到点再乘回来**"，
> 不是一个"到底就衰减"的调度器。

### 1.4 🔴 最容易踩的坑：`auto_scale_lr`

```python
auto_scale_lr = dict(base_batch_size=16, enable=True)
```

基座 `schedule_1x.py` 里是 `enable=False`，**DeCoDet config 把它改成了 `True`**。

按 MMEngine 的 `auto_scale_lr` 语义，`scale = 实际总 batch / base_batch_size`，
然后 `真实 lr = lr × scale`。

> [!danger] 后果
> 你若按 config 默认 **1 张卡 × batch_size 2** 训练：
> `scale = 2 / 16 = 0.125` → **真实 lr = 0.02 × 0.125 = 0.0025**
> 比论文的 0.02 **小了 8 倍**，训练曲线完全不是一回事。
>
> 👉 **复现前必做二选一**：
> - 把 `auto_scale_lr.enable` 改成 `False`，或
> - 把 `base_batch_size` 改成 `2`（或你的真实总 batch）
>
> 这条已同步记进 [[04-复现必查项与坑]]。

> [!danger] 🔴 而且还要再叠一层 `ConstantLR` —— 单卡实际 lr 比论文小 **24 倍**
> `vfnet/DeCoDet_vfnet_...` 的 `ConstantLR` 窗口是 `end=1500`，**第 0 步就把 lr ÷3**（§1.3）。
> 两件事都是乘法，先后顺序不影响乘积：
>
> ```
> 0.02 (config) × (2/16 auto_scale_lr) × (1/3 ConstantLR) = 0.000833
> ```
>
> | 口径 | lr | 相对论文 0.02 |
> |---|---|---|
> | 论文写的 | 0.02 | 1× |
> | 只算 `auto_scale_lr` | 0.0025 | 1/8 |
> | **`auto_scale_lr` + `ConstantLR`** | **0.000833** | **1/24** ⚠️ |
>
> 👉 单卡复现必须**两处一起改**：`auto_scale_lr.enable=False`（或 `base_batch_size=2`），
> **且**把 `ConstantLR` 换成你想要的行为（或直接删掉这段）。

> [!tip] 一个容易混淆的点
> config 里有两个看起来都像"层数"的参数：
> - **`stacked_convs=3`** ← 这是 **MSDP 的 M**（论文消融的那个 M）
> - **`condition_layers=1`** ← 这是 **DCK 内部 bottleneck 的堆叠深度**，**不是** M
>
想调 M 改 `stacked_convs`；想加深 DCK 的生成器改 `condition_layers`。
👉 调错参数会得到完全不同的算力账。

### 2.2 🔴 最容易读错的一点：16/19 的模型都用了 PDFT

论文原话：

> "Fog-specialized detectors maintain their original protocols, while **all other models employ our progressive fine-tune approach** from Algorithm 1"

| 模型 | 是否用 PDFT |
|---|---|
| IAYOLO / TogetherNet / MS-DAYOLO | ❌ 保持原协议 |
| **其余 16 个**（YOLOv3 ~ Deform DETR） | ✅ **全部用 PDFT** |

> [!warning] 这条一旦忽略，整张表都会被读反
> Table 3 里 **VFNet 那一行的真实域 35.6，已经是 PDFT 之后的结果**；
> 而 Table 4 里 **VFNet baseline 的真实域是 25.6（没用 PDFT）**。
>
> 所以：
> - **Table 3 的 VFNet ≠ Table 4 的 baseline**，差 **+10.0**
> - 论文说"18 个模型都用了 PDFT"是**论文正文里必须交代、但表格里没标**的协议差异

> 👉 任何"DeCoDet 比 XX 高 X 点"的对比，**都要先确认双方有没有用 PDFT**。

### 2.3 「速度 / 效率」这句话要加限定

论文说 DeCoDet "maintaining **higher speed** (59.7 FPS) and efficiency (34.62M parameters)"。

但把全表摊开看：

> [!tip] 正确的读法

>
> 👉 **论文那句话不算错，但省略了限定条件。** 引用时最好写"在达到 SOTA 精度的模型中速度最快"。

> MSDP 算出来的深度图**本身没人要** —— 它只是给 DCK 造核用的中间产物。
> 没有 DCK 消费它，这 36.8 GFLOPs 就是白烧。
> 📌 这条与 [[05-DeCoDet原理精读]] §「MSDP 单独上 = 纯亏」的结论**互相印证**（论文表 4 与你自己的推导结论一致）。

#### ③ DCK —— **真正的引擎**

| | mAP–Test | mAP–Real | 相对上一行 |
|---|---|---|---|
| + PDFT + MSDP | 49.8 | 35.8 | – |
| **+ PDFT + MSDP + DCK** | **50.6** | **36.9** | **+0.8 / +1.1** |

而代价只有 **+9.27 GFLOPs**（221.14 → 230.41）、**+0.02M 参数**。

> [!tip] 关键对比
> | 手段 | GFLOPs 增量 | 真实域 mAP 增量 | 性价比 |
> |---|---|---|---|
> | MSDP | +36.8 | +0.2 | ❌ 极差 |
> | **DCK** | **+9.3** | **+1.1** | ✅ 好 |
> | PDFT | **0** | **+10.0** | ✅✅ 极好 |
>
> 👉 **DCK 是唯一值得算力的模块**，而且它**必须配 MSDP**（MSDP 是它的输入）。

#### ④ SIRLoss —— **单独几乎白给**

| | mAP–Test | mAP–Real |
|---|---|---|
| + PDFT + MSDP | 49.8 | 35.8 |
| + PDFT + MSDP + SIRLoss | 50.0 (+0.2) | 35.9 (+0.1) |

- 有 DCK 无 SIRLoss：50.6 / 36.9

> [!tip] 这就是论文说的 "complementary effects"（互补效应）
> SIRLoss 的作用**不是单独提升深度估计精度**，
> 而是**让 DCK 用的深度先验更干净**，从而放大 DCK 的效果。
> 三者耦合：MSDP 产深度 → SIRLoss 净化深度 → DCK 把深度变成核。
> 👉 **单看 SIRLoss 那一行会低估它。**

#### ⑤ 全量组合

#### **K（DCK 核宽）—— 全表最大的悬崖**

| K | mAP–Test | mAP–Real | 相对 K=7 |

| 3 | **42.9** | **31.2** | **−9.1 / −6.8** 🔴 |

> [!danger] K=3 直接崩掉 9.1 个点
> 这是全表**唯一一处断崖式下跌**，也是最值得深挖的现象。
>
> **直觉**：DCK 造的是 7×7 的**空间自适应感受野**。
> 雾把远处小目标的纹理抹平了，**核必须够大才能"捞"回残存的边缘证据**。

>
> 📌 这条在 [[05-DeCoDet原理精读]] 里有更细的机理讨论（DCK ≈ 深度条件化的可变形卷积）。
> 👉 **反过来说："调制范围"是 DCK 的命门，不是随便加个模块就能用。**

| G | Para(M) | GFLOPs | mAP–Test | mAP–Real |
|---|---|---|---|---|

| 64 | 34.92 | **249.86** | 51.6 | 37.2 |

- G=1 → 16：**+2.8 / +3.7**，几乎免费（+6 GFLOPs）→ **性价比最高的一跳**
- G=16 → 64：**−0.4 / −0.8**，却多 **+19.45 GFLOPs** → **纯亏**

> [!tip] 读表口诀
> **G 越大，卷积分组越细、每组共享的通道越少 → 表达力越强，但算力线性涨。**
> 论文选 16 是"再往上就没收益了"的拐点。

#### **M（MSDP 卷积数）—— 机载算力受限时的最优解**

| M | Para(M) | GFLOPs | mAP–Test | mAP–Real |
|---|---|---|---|---|
| **1** | **31.39** | **156.68** | 50.1 | 35.6 |
| 2 | 33.16 | 202.75 | 50.6 | 36.0 |
| **3** | 34.61 | 230.41 | **52.0** | **38.0** |

> [!important] 🔥 M=1 这一行最反直觉，值得单独想清楚
> **M=1 的完整 DeCoDet（31.39M / 156.68 GFLOPs）比纯 VFNet baseline（32.71M / 184.32 GFLOPs）还更小更省！**
> 但 mAP 反而是 50.1 / 35.6（baseline 是 49.5 / 25.6）。
>
> **怎么解释？**（论文没解释，这是个真实的开放问题）
> - 一个方向：DeCoDet 的 head 结构（DCK 用 1×1 bottleneck 生成核）本身比 VFNet 原生 head 更省，
>   所以即使加了一层 MSDP，总参数仍低于 baseline。
> - 但要小心：baseline 行（32.71M）是**纯 VFNet**，而 M=1 行是**完整 DeCoDet**，
>   **两者的 head 结构并不相同**，参数量不是"同一结构加/减"的可比口径。
>
> 👉 **诚实结论**：这条**不能直接说"MSDP 不增加参数"**，
> 只能说「**在机载算力预算下，M=1 是性价比最高的配置**」——
> 156.68 GFLOPs 比 baseline 还低，mAP 却高 0.6 / 10.0。
> 📌 与 [[05-DeCoDet原理精读]] §⑦「算力紧张（机载）：M=1」的结论一致 ✅

#### **β（SIRLoss 权重）**

| β | mAP–Test | mAP–Real | 相对 β=0.2 |

| 1.0 | 50.1 | 36.9 | −1.9 / −1.1 |

> [!tip] β 的含义（别搞错）
> β 是 `loss_seg.loss_weight`，**整个深度损失乘 0.2**，

> 它支持「**深度调制让特征更聚焦于目标区域**」，
> 也就是 DCK 的作用机制 —— 与 Table 4 里 DCK 独占 +1.1 的结论方向一致。
> ⚠️ 但 Grad-CAM 是**定性**证据，**不能当作 DCK 有效的证明**（证明靠 Table 4 的消融）。

### 5.2 (b) 深度可视化

- 上排 = **GT 深度图**（真值），下排 = **网络预测**的深度图
- 论文结论：传统深度估计输出**平滑、漏掉小目标**；
  DeCoDet 在**高层做全局对齐、在局部强调检测线索** → 对"被雾遮住的小目标"更敏感

### 5.3 (c) 鲁棒性验证 —— 🔥 深度标注质量决定上限

做法：给**训练用的深度图**加**不同方差的高斯噪声**，看性能怎么掉。

- 论文结论：噪声越大性能越掉，**高噪声时尤其明显**
- 推论（论文原话）："enhancing **depth estimation accuracy** is vital for future performance improvement"

> [!important] 这条对你的意义
> 这是 HazyDet **数据价值**的最强证据：
> **深度标注越准，检测越好** —— 深度不是可有可无的辅助信号，它直接决定天花板。
>
> 👉 也意味着：**如果你要在这条线上做研究，深度标注的精度就是你的杠杆。**
> 而 HazyDet 的深度是 **Metric3D 生成的伪标签**（不是激光雷达真值）——
> Table S1 已经显示，换个深度模型性能就变（见 §6.1）。
> 📌 **这给了一个非常明确的方向：更好的深度估计 → 更好的检测。**

### 6.1 Table S1：深度损失 & 深度估计模型的对比

**(a) 深度损失函数**

| Loss function | mAP–Test | mAP–Real |
|---|---|---|
| L1 loss | 43.2 | 30.2 |
| SmoothL1 | 48.9 | 34.3 |
| MSE Loss | 49.9 | 36.0 |
| **SIR Loss** | **52.0** | **38.7** |

> [!tip] 怎么读
> L1 → SIR 一路涨 **+8.8 / +8.5**，和 Table 4 里「SIRLoss 单独只 +0.2」不矛盾：
> Table 4 是在 **DCK 已经在场**的前提下看 SIRLoss 的**边际**贡献；
> Table S1 是**从头换损失函数**看**绝对**差异。
> 👉 **边际 vs 绝对，是读消融表最容易混的两件事。**

**(b) 深度图来源（不同深度估计模型）**

| Model | mAP–Test | mAP–Real |
|---|---|---|
| VA-DepthNet | 43.2 | 30.2 |
| ZoeDepth | 47.3 | 32.3 |
| IEBins | 48.5 | 32.1 |
| UniDepth | 49.3 | 34.3 |
| **Metric3D**（本文采用） | **52.0** | **38.7** |

> [!important] 🔥 这张表是全篇**最直接指向你选题**的一张
> 深度估计模型的强弱，**几乎线性地**传导到检测性能：
> VA-DepthNet（43.2）→ Metric3D（52.0），**差 8.8 mAP**。
>
> **这说明什么？**
> 在 HazyDet 上，"更好的深度估计" 和 "更好的检测器" 收益是**同一个量级**的。
> 而深度估计是一个**可以独立换、可以独立研究**的模块。
>
> 👉 **选题候选 A**：
> **"更强的深度估计 → 更好的雾天检测"** 这条因果链，在 HazyDet 上只被验证了"相关性"，
> 没人系统研究过"**如何把深度估计的提升高效传导到检测**"（比如蒸馏一个轻量深度先验、
> 让 DCK 对深度误差鲁棒）。这是**空白**。
>
> 👉 **选题候选 B**：
> Fig 5(c) 已经证明「深度噪声会拖垮检测」，但**没有任何工作让 DCK 对深度噪声鲁棒**
> （比如不确定性加权、置信度门控、多深度假设）。
> 📌 这与 [[paper-notes/论文精读/3-HazyDet精读/03-深度标注与被浪费的多模态线索]] 那条线完全接得上。

### 6.2 Fig S5：不同微调策略的对比（PDFT 的必要性论证）

对比三种拿真实域检测器的方式，图 (b) 是各模型组的结果：

| 策略 | 说明 | 结论 |
|---|---|---|
| ① 只在**真实数据**上微调 | 直接从源域跳到目标域 | ❌ **严重域移 + 过拟合**，所有模型都次优 |
| ② 只在**合成数据**上微调 | 跳过中间域 | ⚠️ 有明显提升，但没吃到"桥"的作用 |
| ③ **PDFT**（本文） | 合成 → 真实 渐进 | ✅ **对所有模型组都有增益** |

论文的三段论（§B.2）：
1. 直接在真实数据上微调 → 域移严重 + 过拟合（真实训练集只有 400 张）
2. 只用合成数据 → 语义特征有帮助、样本量足以抑制过拟合
3. 所以**用合成数据当"桥"** → PDFT 有效

> [!tip] 关键设计
> PDFT 的价值**不在于它是个新损失或新模块**，
> 而在于它**把"中间域"显式建模出来了**。
> 400 张真实图 → 8000 张合成图 → 400 张真实图（两段式）。
> 👉 这是**课程学习 / 域过渡**的思想，只是被包装成了"检测器的两阶段微调"。

论文展示了 DeCoDet 的**漏检**案例（Fig S6(a) Missed detection），
以及合成雾与真实雾场景的检测结果对比。

## 8. 自测题（能答出来说明实验部分读透了）

<details>
<summary>Q1：Table 3 里 VFNet 真实域 35.6，Table 4 里 VFNet 真实域 25.6，差 10.0，为什么？</summary>

**A**：Table 3 的 VFNet **已经用了 PDFT**（论文说除 3 个雾专用模型外其余全用 PDFT）；
Table 4 的 baseline 是**未加 PDFT 的纯 VFNet**。
两个数是**不同训练协议**下的，不能直接比。
📌 这是 Table 3 最重要的隐藏协议差异。
</details>

<details>
<summary>Q2：为什么 DeCoDet 在 Table 3 只赢 1.5 个点，论文却敢叫 SOTA？</summary>

**A**：因为它同时赢了**速度**（59.7 FPS，在达 SOTA 精度的模型中最快）和**真实域**。
但要说清楚：**合成域只赢 0.4**，且「合成 Bus」这一列它只排第三。
👉 正确的表述是"**真实域 SOTA + 同精度下最快**"，不是"全面碾压"。
</details>

<details>
<summary>Q3：MSDP 明明在论文卖点里，为什么 Table 4 显示它单独用几乎没用？</summary>

**A**：因为 **MSDP 是中间产物生产者，不是消费者**——
它算出的深度图本身不参与检测，只有 DCK 拿它造核才有用。
单独上 = 白烧 36.8 GFLOPs。
📌 这也解释了为什么"深度只在训练期用"仍然成立：推理时 DCK 用的是**特征生成的核**，
不需要深度图本身。
</details>

<details>
<summary>Q4：Table 5 里 PSNR 最高的 C2PNet，为什么 mAP 还不如 PSNR 倒数的 RIDCP？</summary>

**A**：因为 **PSNR/SSIM 衡量的是"像素级还原得像不像"，不是"目标特征保不保得住"**。
去雾会把低对比度的雾中目标一起抹平，像素指标好了，**检测证据反而没了**。
👉 所以"用 PSNR 选去雾模型"是个陷阱。
</details>

<details>
<summary>Q5：Table 3 和 Table 4 的 DeCoDet 真实域 mAP 差 0.7，引用时该写哪个？</summary>

**A**：看语境 —— 谈 SOTA 对比写 **38.7**（Table 3），谈消融分析写 **38.0**（Table 4）。
**并在同一句话里注明"Table 3 记为 38.7"**。
参数量 / GFLOPs 同理，**不要跨表混用**。
📌 这是论文自身的不一致，不是你读错了。
</details>

<details>
<summary>Q6：Fig 5(c) 加高斯噪声那个实验，证明了什么？</summary>

**A**：证明 **深度标注质量直接决定检测上限**——
噪声越大性能掉得越多，深度估计精度是未来改进的关键。
👉 推论：HazyDet 的深度是 Metric3D **伪标签**（不是激光雷达真值），
而 Table S1 显示换深度模型能差出 8.8 mAP
→ **"更好的深度估计"是一个和"更好的检测器"收益同量级的独立方向**。
</details>

<details>
<summary>Q7：单卡训练官方 config，lr 会是多少？为什么？</summary>

**A**：**0.0025**，不是论文的 0.02。
因为 config 里 `auto_scale_lr = dict(base_batch_size=16, enable=True)`，
MMEngine 会按 `scale = 实际总 batch / base_batch_size = 2/16 = 0.125` 缩放 lr。
👉 复现前必须改 `enable=False` 或 `base_batch_size=2`。
</details>

<details>
<summary>Q8：M=1 的完整 DeCoDet 只有 31.39M / 156.68 GFLOPs，比纯 VFNet baseline 还小。说明什么？</summary>

**A**：**不能直接说"MSDP 不增加参数"** —— 两行的 head 结构并不相同，参数量不是同口径可比。
正确结论是「**在机载算力预算下，M=1 是性价比最高的配置**」：
156.68 GFLOPs（低于 baseline 的 184.32），mAP 却是 50.1 / 35.6 vs baseline 的 49.5 / 25.6。
📌 论文没解释这个现象，是个真实的开放问题。
</details>

## 9. 复现 checklist（实验部分相关）

- [ ] 确认 `momentum` 用 0.937（config）还是 0.938（论文）
- [ ] 确认用的是 `ConstantLR`（config）而不是自己加 `LinearLR` warmup
- [ ] Table 3 的对比要**自己实现 PDFT**，否则 16 个模型全对不上
- [ ] 深度图用 **Metric3D** 生成的（对应最佳结果），别用别的深度模型
- [ ] `loss_seg.loss_weight=0.2`（β）别忘
- [ ] 深度损失用 `SIRLOSS`（`log=True, smooth=True, epsilon=0.3`），别用默认 SmoothL1
- [ ] `stacked_convs=3`（M）不是 `condition_layers`（DCK 内部深度）
- [ ] 算力紧张时改 `stacked_convs=1` —— 记得它比 baseline 还省
- [ ] 想复现 **38.0** 用 Table 4 口径；想复现 **38.7** 用 Table 3 口径；**别混**
