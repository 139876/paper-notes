# 04 · 复现必查项与坑

> [!abstract] 本讲要回答
> 我想把 HazyDet 跑起来（或至少跑通一个 baseline），**必须先检查哪几件事**？
> 官方仓库里有哪几个**会直接让结果错掉**的坑？

> ⚠️ **说明**：本讲是**纸面核对**结果（读 config 与源码得出），
> **没有实际训练过**。等真上手时按这个清单逐条对一遍即可。

---

## 0. 一句话总览

> **HazyDet 的坑不在模型，在"数据 + 配置"的缝隙里。**
> 模型部分（TOOD / FCOS / ATSS）是 mmdet 现成的，能跑；
> **跑出来的数字对不对，取决于你有没有发现下面这 5 个坑。**

---

## 1. 坑 ①：`data_root` 是硬编码绝对路径，而且**两个 config 还不一样**

```python
# configs/_base_/datasets/hazydet_det.py
data_root = '/opt/data/private/fcf/HazyDet-365K/data/HazyDet365K/'

# configs/_base_/datasets/hazydet_dual.py
data_root = '/opt/data/private/fcf/Public_dataset/HazyDet-365K/data/HazyDet365K/'
```

| 问题 | 后果 |
|---|---|
| 路径是**别人机器上的绝对路径** | 你必然要改 |
| **单模态版和双模态版路径不同** | 改的时候容易只改一半 → 深度版找不到 `max_depth.txt` |

> 🎯 **为什么这算"坑"而不是"小事"？**
> 因为 `data_root` 是 `_base_` 里的**基类变量**。
> 很多 config 用 `data_root=data_root` 继承它，
> 但**有些 config 会重新写一遍**。你改了 A 文件，B 文件还在用旧路径。
> 👉 **正确做法**：用 `sed` 全局替换，或者在你的自己的 config 里显式覆盖 `data_root`。

### 1.1 目录结构必须严格对上

```
HazyDet365K/
├── train/
│   ├── hazy_images/          ← data_prefix.img='train/hazy_images/'
│   └── train_coco.json       ← ann_file='train/train_coco.json'
├── val/
│   ├── hazy_images/
│   └── val_coco.json
├── test/
│   ├── hazy_images/
│   └── test_coco.json
└── Depth/
    ├── normalized_depth_maps/   ← data_prefix.seg='Depth/normalized_depth_maps/'
    └── max_depth.txt            ← max_depth_path=data_root+'Depth/max_depth.txt'
```

> ⚠️ **`max_depth.txt` 的格式**：第一行是**表头**，代码里 `f.readlines()[1:]` 会跳过它。
> 如果你手搓这个文件，第一行随便写点东西当表头，**不要留空行**——
> 空行会被 `if len(parts) == 2` 跳过（安全），但**第一行如果正好是"图名 深度"**，
> 就会**丢掉第一张图的深度**，而后面 `_load_seg_map` 找不到就 `raise ValueError`。

## 2. 坑 ②：`filter_cfg` 训练有、验证没有

```python
# train
filter_cfg=dict(filter_empty_gt=True, min_size=32)
# val / test —— 没有这一行
```

| 影响 | 说明 |
|---|---|
| **训练分布 ≠ 验证分布** | 训练时"所有目标都 < 32px"的图被整张丢掉，验证时不丢 |
| **AP_small 偏低** | 验证集里的小目标图，模型没见过 → 小目标指标天然低 |
| **指标不可比** | 别人用 `min_size=32` 你用 32（或改小），数字没有可比性 |

> 📌 **报数字时必须写清楚**：`min_size=32`、训练集 filter 规则。
> 不写清楚，**你的结果没法和别人比** —— 这是审稿人第一个抓的点。

---

## 3. 坑 ③：`num_classes=80` —— ATSS 配置里的真实 bug

`configs/atts/atts_r50_fpn_1x_hazydet.py` 第 34 行：

```python
bbox_head=dict(
    type='ATSSHead',
    num_classes=80,        # ⚠️⚠️ HazyDet 只有 3 类！这里应该是 3
    ...
)
```

而 `TOOD` 和 `FCOS` 的 HazyDet 配置里都是对的：

| 配置 | `num_classes` | 对不对 |
|---|---|---|
| `configs/tood/tood_r50_fpn_1x_hazydet.py` | 3 | ✅ |
| `configs/fcos/fcos_r50_1x_hazydet.py` | 3 | ✅ |
| `configs/DeCoDet/DeCoDet_r50_1x_hazydet.py` | 3 | ✅ |
| **`configs/atts/atts_r50_fpn_1x_hazydet.py`** | **80** | ❌ **BUG** |

> ⚠️ **这个 bug 的表现形式很隐蔽**
> `num_classes=80` 不会报错，训练也能跑。
> 但：
> - 分类头输出 80 个通道，**其中 77 个永远没有正样本**
> - Focal Loss 会被大量**无效负类**拉偏
> - mAP **明显低于**正确的 3 类设置
>
> 👉 **如果你要用 ATSS 当 baseline，第一件事就是把 80 改成 3。**
> 这个坑在 CCFA-Net 的笔记里也记过 —— 见
> [[paper-notes/论文精读/1-CCFA-Net精读/03-CCFA-Net论文精读/10-第9讲-数据集与实验设置|第 9 讲 · 数据集与实验设置]]。

> 📌 **顺便**：HazyDet 只有 3 类，但**COCO 口径的评测**（`CocoMetric`）照样能用，
> 因为 `CocoMetric` 是按 `ann_file` 里的 `categories` 走的，**不是**按 `num_classes`。
> 所以"用 COCO 的评测流程"和"只有 3 类"不矛盾。

## 4. 坑 ④：`lr` / `momentum` / `auto_scale_lr` 三处覆盖，**极易算错**

### 4.1 基类 `schedule_1x.py` 的默认值

```python
train_cfg = dict(type='EpochBasedTrainLoop', max_epochs=12, val_interval=1)
param_scheduler = [
    dict(type='LinearLR', start_factor=0.001, by_epoch=False, begin=0, end=500),
    dict(type='MultiStepLR', begin=0, end=12, by_epoch=True,
         milestones=[8, 11], gamma=0.1)
]
optim_wrapper = dict(
    type='OptimWrapper',
    optimizer=dict(type='SGD', lr=0.02, momentum=0.9, weight_decay=0.0001))
auto_scale_lr = dict(enable=False, base_batch_size=16)
```

### 4.2 每个 config 自己的覆盖

| 配置 | lr | momentum | wd | auto_scale_lr | 其他覆盖 |
|---|---|---|---|---|---|
| 基类 `schedule_1x` | 0.02 | 0.9 | 1e-4 | **False** | — |
| `tood_..._hazydet.py` | **0.01** | 0.9 | 1e-4 | False（继承） | — |
| `atts_..._hazydet.py` | **0.01** | 0.9 | 1e-4 | False（继承） | `num_classes=80` ❌ |
| `DeCoDet_r50_1x_hazydet.py` | **0.01** | **0.937** | 1e-4 | **True**, base=16 | `clip_grad(max_norm=35)`、`bias_decay_mult=0`、`bias_lr_mult=2.0`、额外 `ConstantLR`(×0.3333, 500 iter) |

### 4.3 ⚠️ `auto_scale_lr` 到底怎么算

mmdet 的 `auto_scale_lr` 逻辑：

$$
\text{lr}_{\text{actual}} = \text{lr}_{\text{config}} \times \frac{\text{batch\_size}_{\text{actual}}}{\text{base\_batch\_size}}
$$

| 场景 | batch_size（总） | 实际 lr |
|---|---|---|
| 官方：8 卡 × 2 = 16 | 16 | `0.01 × 16/16 = 0.01` ✅ 不变 |
| 单卡 batch 2 | 2 | `0.01 × 2/16 = 0.00125` ⚠️ **小了 8 倍** |
| 单卡 batch 16 | 16 | `0.01` ✅ |
| 8 卡但 batch 改成 4 | 32 | `0.01 × 32/16 = 0.02` |

> 🎯 **类比**
> 官方配方是"**8 个人抬一个箱子，每人拿 1/8 的力**"。
> 你一个人来，要么**使同样的总力**（lr 不变，batch 保持 16），
> 要么**用 1/8 的力**（lr 缩小到 0.00125）—— 后者当然训不出论文的效果。
>
> 👉 **单卡复现的正确做法**：
> ① `batch_size=16` + `lr=0.01`（推荐，最省心）
> ② 或者 `batch_size=4` + `lr=0.0025`，并**关掉** `auto_scale_lr` 自己算

> ⚠️ 注意 `DeCoDet` 的 config 里 `auto_scale_lr = dict(base_batch_size=16, enable=True)`，
> 而**基类里是 `enable=False`** —— **config 里写的是覆盖，不是叠加**，
> 所以最终生效的是 `enable=True`。读 config 时要读**合并后的最终值**，不是只看自己那一个文件。

### 4.4 ⚠️⚠️ DeCoDet 有**两段**学习率调度

```python
param_scheduler = [
    dict(begin=0, by_epoch=False, end=500,
         factor=0.3333333333333333, type='ConstantLR'),   # ← 额外的一段
    dict(begin=0, by_epoch=True, end=12, gamma=0.1,
         milestones=[8, 11], type='MultiStepLR'),
]
```

> ⚠️ **这段 `ConstantLR` 会和基类的 `LinearLR` warmup 叠加**：
> 基类的 `LinearLR(start_factor=0.001, end=500)` 是 500 iter 内把 lr 从 0.001 线性升到 1.0，
> DeCoDet 又叠了一个 500 iter 内 ×0.3333 的常数。
> 👉 **前 500 iter 的实际 lr = 0.01 × LinearLR曲线 × 0.3333**。
>
> 这不是 bug，但**你必须知道**，否则你会以为"DeCoDet 的 warmup 怎么这么低"。
> 👉 **要复现 DeCoDet，就照抄它的 config，别只抄基类。**

## 5. 坑 ⑤：论文的 schedule 和仓库的 schedule **对不上**

这是本套笔记里跨第 1 篇和第 3 篇都查到的**硬冲突**：

| 项 | CCFA-Net **论文** | 官方仓库 `schedule_1x.py` | 是否一致 |
|---|---|---|---|
| 训练轮数 | **24** epoch | **12** epoch | ❌ |
| milestones | **[16, 22]** | **[8, 11]** | ❌ |
| momentum | **0.938** | **0.9** | ❌ |
| lr | 0.01 | 0.01（基类 0.02，被 config 覆盖） | ✅ |
| weight decay | 0.0001 | 0.0001 | ✅ |
| warmup | 500 iter | 500 iter | ✅ |
| 输入尺寸 | 1333×800 | 1333×800 | ✅ |
| flip | 0.5 | 0.5 | ✅ |

> ⚠️ **⚠️ 最致命的一条：仓库里根本没有 CCFA-Net 的代码**
>
> 全仓检索 `CCDD` / `CFFM` / `MFAM` / `CCFA` → **0 命中**。
> 仓库提供的是 **21 个 baseline config**（TOOD、FCOS、ATSS、DeCoDet、YOLOv3、YOLOX…）
> + HazyDet 数据集 + TOOD 头 + 深度头。
>
> 👉 **结论**：CCFA-Net 的 54.6 **无法通过这个仓库直接复现**，
> 仓库的价值是：**给你 HazyDet 数据 + 官方 baseline + 复现所需的全部环境配置**。
>
> 📌 **这也意味着**：
> ① 你的工作（复现 CCFA-Net）**本身就可能是一个选题**；
> ② 论文和仓库不一致的 24 vs 12 epoch，**你可以自己跑一遍来判定谁对**。

## 6. 📋 上手清单（照着走一遍）

### 阶段一 · 环境（半天）

- [ ] 建好 conda 环境，装 `mmengine` / `mmcv` / `mmdet` / `mmpretrain`
- [ ] 确认 **CUDA 版本**和 mmcv 的编译版本**匹配**（这是最常见的翻车点）
- [ ] `pip install -e .`（仓库根目录），确认 `CCFANet` 包能 import

### 阶段二 · 数据（半天 ~ 两天）

- [ ] 下载 HazyDet（**注意申请/下载页面**，数据集在 GitHub Releases 或官网）
- [ ] 按第 1 节的目录结构解压（`train/ val/ test/ Depth/`）
- [ ] 确认 `max_depth.txt` 存在且格式正确（**第一行是表头**）
- [ ] 改 `data_root`（**两个文件都改**）

### 阶段三 · 先跑通 baseline（1~2 天）

- [ ] 跑 `configs/tood/tood_r50_fpn_1x_hazydet.py`（**这个配置最干净**，是 CCFA-Net 的 baseline）
- [ ] 先跑**小规模 smoke test**（比如 train 划 50 张、跑 1 个 iter），确认 pipeline 通
- [ ] 再跑完整 12 epoch

### 阶段四 · 对账（关键！）

对照这张表，**每一项都要对上**：

| 对账项 | 期望值 | 出处 |
|---|---|---|
| TOOD baseline mAP | **50.8** | CCFA-Net 论文 Table 8（消融第一行） |
| TOOD + CCDD | 52.3 | 同上 |
| TOOD + CFFM | 52.9 | 同上 |
| TOOD + MFAM | 52.7 | 同上 |
| TOOD + CCDD + MFAM | 54.1 | 同上 |
| **CCFA-Net 完整** | **54.6** | CCFA-Net Table 2 |
| 分类别（Car/Truck/Bus） | 62.2 / 37.5 / 64.2 | CCFA-Net Table 2 |

> ⚠️ **对不上怎么办？**
> 按这个顺序排查：
> 1. **训练集 filter 规则**对不对？（坑 ②）
> 2. **lr 和实际 batch size** 匹配吗？（坑 ④）
> 3. **epoch 数 / milestones**？（坑 ⑤）
> 4. **`num_classes` 是 3 还是 80**？（坑 ③）
> 5. **预训练权重对不对**？TOOD 配置用 `torchvision://resnet50` + `style='pytorch'`；
>    DeCoDet 用 `open-mmlab://detectron/resnet50_caffe` + `style='caffe'`。
>    ⚠️ **`style` 和 checkpoint 必须配套**，否则 BN 统计和卷积布局对不上，性能会莫名其妙差一截。

## 7. 📌 关于「不跑代码」阶段该做什么

> 📌 **你现在是理论学习为主**，这一讲先当**checklist**存着。
> 真正需要你"现在就懂"的是这三条：
>
> 1. **训练/验证 filter 不一致** → 理解**评测协议**为什么必须公开
> 2. **`num_classes=80` 是真 bug** → 理解**"数据集类别数"和"模型输出维度"是两件事**
> 3. **lr 与 batch size 的换算** → 理解**"超参数"不是孤立的数字，而是与 batch 绑定的**

这三条都属于**方法论**，换任何数据集、任何论文都成立。

## 8. ❓ 自测

1. `num_classes=80` 这个 bug 为什么不会让训练直接报错？它会怎么影响 mAP？
2. 你只有一张 24G 显卡，想复现 TOOD baseline。`batch_size=2` + `auto_scale_lr=True` + `base_batch_size=16` 会发生什么？该怎么改？
3. DeCoDet 的 config 里有 `ConstantLR(×0.3333, 500iter)`，基类里还有 `LinearLR` warmup(500iter)。最终前 500 iter 的 lr 曲线是什么形状？
4. 论文说 24 epoch，仓库说 12 epoch。你应该采信哪个？为什么不能直接采信论文？
5. 为什么"评测用 COCO 协议"和"数据集只有 3 类"不矛盾？

<details>
<summary>👉 折叠答案</summary>

1. 因为 `num_classes` 只决定分类头的输出通道数，多出来的 77 个通道不会报错，只是**永远拿不到正样本**。Focal Loss 会把大量无效负类算进去，**分类置信度被稀释**，最终 mAP 明显偏低（且 Truck/Bus 受损更重，因为它们的正样本本来就少）。

2. 实际 lr = 0.01 × (2 / 16) = **0.00125**，比官方小 8 倍 → 收敛严重不足，mAP 会明显偏低。改法：① 单卡把 batch_size 提到 16、lr 保持 0.01（最省心，但显存可能不够）；② 或 batch_size=4 + lr=0.0025 + 关掉 auto_scale_lr 自己算；③ 或用梯度累积（**注意：梯度累积不会改变 `auto_scale_lr` 的计算**，得手动对齐）。

3. 两条曲线的**乘积**：前 500 iter 内，`LinearLR` 从 0.001 线性升到 1.0，再乘上固定的 0.3333。所以是一条**从 0.000333 线性升到 0.3333** 的斜坡 —— 起点比基类更低，终点也比基类低。

4. **两个都不能盲信，要自己跑出来判定**。理由：论文写的是"最终版"的设置，仓库可能停在某个中间版本；也可能是作者一边改一边提交只更新了代码没更新论文。正确做法：跑 12 epoch 和 24 epoch 两组，看哪组更强。**这就是"对账"的意义** —— 数字对不上时，先怀疑配置，别急着怀疑方法。

5. 因为 `CocoMetric` 是**按 `ann_file` 里的 `categories` 列表**来计算 AP 的，评测协议（COCO 的 101 点插值、面积分档）可以套用在任意类别数的标注文件上。`num_classes` 是**模型**的事，`categories` 是**数据**的事，两者独立。

</details>
